Caps aggregate submitted packets/s across all workers. Selecting a cap automatically uses Unlimited rate policy so this is the only limiter. Pacing happens in small fixed batches so the DHMP packet hot path stays allocation-free.

Receive mode

Sequential publishes every complete record. Latest publishes only the newest record. Latest + Native Ring-3 still publishes only that newest record, while retaining N-2/N-1/N receive-side for smoothing.

Confirmation mode

No confirm is the normal one-way path. Application ID confirm reuses the existing 64-bit application ID already present in each 16-byte stress record and packs two IDs into each 16-byte return record. Full echo returns and byte-compares the same 16-byte records. Forward packet shape never changes. Confirmation modes require Sequential receive mode.

Rate policy

Unlimited bypasses local rate accounting and submits as fast as the worker/backend can run. RejectWindow enforces a one-second Pmax budget. SmoothPacing deliberately spaces submissions over time.

Core processor ceiling is a separate single-thread tight-loop measurement using one outer timer around millions of DhmpPacketProcessor calls, comparable to the historical core-sanity benchmark. Instrumented server path includes the server facade, publication callback and per-sample timing. Allocation telemetry is process-wide and sampled once per second; at high packet rates, steady-state DHMP should converge near 0 B/packet. The four allocation probes are isolated single-thread measurements over 250,000 calls using one outer allocation counter; the full-path probe uses Unlimited + No confirm to isolate baseline DHMP overhead. This is an in-process server stress benchmark. It exercises the actual DHMP client validation/send path and server packet processing through an in-memory direct-IP boundary so NIC, browser and HTTPS speed do not cap the protocol measurement. It is not a raw IPv6 wire-throughput result.

Browser stays out of the hot path

Only one JSON snapshot per second crosses HTTPS. The high-rate records never go to the browser.

Large packets expose throughput

Each packet contains only fixed 16-byte DHMP application records. Larger packets reduce per-packet call overhead and reveal aggregate processing capacity.

Mode-aware correctness

Sequential expects every record to be published. Latest expects exactly one published record per accepted packet. Native Ring-3 does not change that publication count. Confirmation modes use Sequential publication: Application ID returns compact batched IDs, while Full Echo returns the full record bytes.
