Caps aggregate submitted packets/s across all workers. Selecting a cap automatically uses Unlimited rate policy so this is the only limiter. Pacing happens in small fixed batches so the DHMP packet hot path stays allocation-free.

Receive mode

Sequential receives into Ring-3 and transfers every record into the FIFO. UnsafeSequential writes directly into FIFO-owned memory and skips Ring-3. Latest keeps the three-slot newest-state Ring-3 and supports independent grabbing / Native Smoothing. UnsafeLatest is the minimal newest-state comparison: one reusable receive slot, synchronous borrowed publication, no Ring-3 history, no independent grabber and no smoothing.

Confirmation mode

No confirm is the normal one-way path. Application ID confirm reuses the first 64-bit application ID field inside the selected fixed-size record and returns it inside one fixed-size confirmation record. Full echo returns and byte-compares the complete selected record. Forward packet shape never changes. Confirmation modes require Sequential receive mode.

Rate policy

Unlimited bypasses local rate accounting and submits as fast as the worker/backend can run. RejectWindow enforces a one-second Pmax budget. SmoothPacing deliberately spaces submissions over time.

Core processor ceiling is a separate single-thread tight-loop measurement. The instrumented server number measures the selected direct receive destination after transport byte movement: Ring-3 for Sequential/Latest, FIFO tail for UnsafeSequential, or one reusable borrowed slot for UnsafeLatest. Sequential includes its Ring-3 → FIFO ownership copy; UnsafeSequential removes that copy; UnsafeLatest also removes Ring-3 history and can only publish synchronously before the slot is reused. This is an in-process logical processing benchmark: NIC/kernel byte movement is deliberately excluded and is measured separately on the Kernel Bypass / Full Report I/O paths.

Browser stays out of the hot path

Only one JSON snapshot per second crosses HTTPS. The high-rate records never go to the browser.

Record size is the packet payload

The selected size is negotiated as one fixed DHMP application record and one DHMP packet payload. A 65,520-byte selection is therefore one 65,520-byte record. On the direct-slot benchmark the transport write itself is outside the timer, so larger records do not imply an extra DHMP copy.

Mode-aware correctness

Sequential, UnsafeSequential, Latest and UnsafeLatest all receive exactly one negotiated record per accepted packet in this benchmark. Unsafe modes change only local storage/publication ownership, not V1 wire bytes. Native Smoothing remains Latest-only. Confirmation modes intentionally remain on normal Sequential only.
