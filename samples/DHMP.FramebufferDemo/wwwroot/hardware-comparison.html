What is measured? The adapter throughput values are published third-party iPerf3 results from one test methodology: six-foot/near distance, uncongested traffic, and the fastest reported band for each adapter. What is calculated? DHMP packets/s and records/s are projections from those published rates; DHMP itself was not run on these five adapters in that external test.

PROJECTION MATH

One physical throughput number, expressed as useful DHMP state

The current benchmark record is 16 bytes. A 1,408-byte DHMP V1 payload therefore contains 88 complete records with no DHMP header, separator or trailer bytes.

records/s = (published Mbit/s × 1,000,000) ÷ (16 × 8) packets/s = (published Mbit/s × 1,000,000) ÷ (1,408 × 8) records/packet = 1,408 ÷ 16 = 88

Do not read this as a measured DHMP speedup over iPerf3. iPerf3 reports useful transfer throughput, not raw Wi-Fi airtime. Proving that DHMP delivers more useful state than TCP/UDP on the same radio requires a controlled same-hardware test that records application bytes, IP bytes, packets/s and interface/link counters for every protocol.

WHY DHMP IS INTERESTING HERE

The data plane does not spend bytes on DHMP framing

0 DHMP header bytes

DHMP V1 data packets contain only complete fixed-size application records. Record boundaries come from the negotiated record size and received IP payload length.

Lower layers still exist

IPv6, Wi-Fi MAC/PHY, encryption, acknowledgements, inter-frame spacing and retransmissions remain real network costs. “Headerless DHMP” never means “zero network overhead.”

The next test is the proof

Run DHMP, UDP and TCP on the same adapter with the same 16-byte state workload. Compare useful records/s against actual interface bytes and packet rate.

ORIGINAL REFERENCE

Why the ROG USB-BE92 is not mixed into the primary five

The ROG USB-BE92 remains a useful reference and an independent review measured 1,768.6 Mbit/s download on 6 GHz. It is intentionally kept out of the main ranking because that review used a different test environment. Mixing it into the same table would make the ranking look more precise than the source data allows.
