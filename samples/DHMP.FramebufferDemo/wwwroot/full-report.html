DHMP POKE

Pre-handshake reachability at the lowest practical managed level

Poke is not a normal DHMP data packet. It is a tiny control-plane exact echo used before negotiation: Mini Poke first proves that the selected DHMP path answers, then Full Echo checks a 1,200-byte exact round trip. The peer returns the same bytes unchanged.

These Full Report numbers are the local Span-based Poke processing ceiling. They show codec + exact-echo cost without socket/network latency. Real connection Poke RTT is measured by the initiating connector with its local monotonic clock.

CANONICAL WIRE PATH

One negotiated record = one DHMP packet

These rows measure exactly one negotiated fixed-size record per packet. Normal Sequential and Latest receive into Ring-3; UnsafeSequential reserves the FIFO tail directly; UnsafeLatest uses one reusable borrowed receive slot with no Ring-3 history. LOW-NOISE AGGREGATE TIMING

10 MB passes, three samples of at least 100 ms

All mode and send-option combinations. Every record size and receive mode runs with Unlimited, RejectWindow and SmoothPacing, each with None, ApplicationId and FullEcho confirmation. After a 50 ms warmup, three samples repeat complete ≥10 MB passes for ≥100 ms each. ns/packet = actual total elapsed ns ÷ total packets; CV shows variation between samples. Rate limits are effectively unlimited: this measures policy overhead. Full-path timing includes copying bytes into the receive slot and processing the return confirmation locally; it is not network throughput. Direct bookkeeping is shared across send options.

LATEST SWEEPER / GRABBER

One fixed three-slot sweep, two grabber modes

Latest and Latest + Native Smoothing use the same sweeper and the same three physical slots. Latest grabs the currently completed slot immediately. Native Smoothing grabs the complete N-2 / N-1 / N window. Neither mode adds Ring-3 work to the packet hot path.
